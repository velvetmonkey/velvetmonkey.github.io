Seal

Seal is a permission gate for AI agents. It sits between an agent and the tools the agent can call: protected actions are blocked by default, and a blocked action runs only after a person approves that exact action, once. Every decision is recorded as a receipt.

A receipt carries a commitment to each field of the decision and an Ed25519 signature over the configuration that produced it. A standalone checker can re-derive the decision from the receipt’s own bytes using only Node.js built-ins. Whether the signature belongs to your operator is established by a verifying key you obtain from a source you already trust — never from the receipt itself.

To see it work, with Node.js installed: npx github:velvetmonkey/seal demo. It runs a blocked tool call, prompts for a one-time approval, executes the approved call, and writes the receipt to disk.

Limits, stated plainly: Seal checks authorization, not intent — if a person approves a harmful request, it runs. Receipts are tamper-evident, not tamper-proof. Prebuilt binaries of the mediating host are released for Linux only (x86-64 and aarch64); other platforms are untested.

Repositories

  • seal — the product a developer installs; the demo and CLI entry point.
  • seal-assurance-kit — the pinned runtime the product fetches by commit and hash; runs with Node alone.
  • seal-check — the external receipt checker, runnable in a browser or from the terminal.
  • mcp-seal-aria — the frozen source of the decision rule, archived at a fixed commit.
  • seal-host — the build and evidence host: the mediating process, signed releases, checksums, and provenance.

Other work

attention-lean

A Lean 4 / Mathlib formalisation of hard-attention expressivity over Boolean cubes. The main theorem shows that for every odd n ≥ 5, strict majority needs at least (n+3)/2 attention heads — one more than its certificate bound — and the five-bit case is exact: k(maj₅) = 4. Structural proofs are kernel-checked with no sorry and no native_decide; enumerated cases are isolated and pinned separately.

SafeMesh

An embeddable library for state that must converge after network partitions. The verified claim is narrow and stated in-repo: five CRDTs (G-Set, G-Counter, PN-Counter, OR-Set, RGA/Text) carry Lean convergence proofs, tied to the Rust implementation by differential tests against a Lean-generated oracle. The event log, wire encoding, and language bindings are tested engineering, not proofs.

Technical note

For the reader who wants the proof story behind Seal: the decision rule is a Lean 4 development, and the theorems cover the mediation kernel — non-bypass and a verifiable record — not the whole deployed system. The shipped binaries are connected to the proofs by byte-exact conformance tests over a corpus, not by a theorem about every compiled instruction. What is proven, tested, assumed, and not claimed is kept in one table: the claims matrix.
