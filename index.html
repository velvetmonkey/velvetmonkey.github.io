Seal

Seal is a permission gate for AI agents. It sits between an agent and the tools the agent can call: protected actions are blocked by default, and a blocked action runs only after a person approves that exact action, once. Every decision is recorded as a receipt.

Seal v1.1, concretely

What it costs you: Node 20 or later, Git, one command and one read-only store directory installed under ~/.local, and one restart of Claude Code when you protect a tool. Linux x86-64 only; on any other platform the installer refuses before changing any file. The artifact’s digest and byte length are pinned in the repository’s SHA256SUMS, and the installer refuses bytes that do not reproduce that pin. The commands are demo, protect, unprotect, status, doctor, verify.

seal protect puts the gate in front of one tool of one MCP server. A guarded call is blocked until a live, one-use approval matches that exact effect. The approval names the exact tool and the exact arguments, states that object-key order and 1 versus 1.0 do not change the match, and is good for one use and two minutes. Then it runs once, and Seal writes a receipt of the decision. Today only the demo signs its receipts, with a key it generates for that run; the protected path writes its receipts unsigned.

Three details worth the space. It never edits your project’s .mcp.json: it installs a Claude Code local override instead, and the test suite asserts the project file is byte-identical by hash before protect, after protect, and after unprotect. Altered bytes refuse: flip one byte of the installed tree and the launcher prints REFUSE artifact_digest_mismatch before it executes anything — ordinary failure modes are staged for real in the test suite, and whatever must refuse does so with a named refusal, not a generic error; a drifted server entry refuses forwarding rather than forward a drifted call. And the demo’s last act writes a file outside the gate and reports that no Seal decision covered it, because Seal is a gate, not a sandbox.

A signed receipt carries a commitment to each field of the decision and an Ed25519 signature, and a standalone checker re-derives it from the receipt’s own bytes using only Node.js built-ins. The shipped checker refuses an unsigned receipt (REFUSE unsealed), so a protected-path receipt is today a plain local record, not checkable evidence. Whether a signature belongs to your operator is established by a verifying key you obtain from a source you already trust — never from the receipt itself.

To see it work, follow the repository’s install: clone, run node scripts/build-dist.cjs, and install the built artifact against the published pin. Then seal demo runs a blocked tool call, prompts for a one-time approval, executes the approved call once, refuses the identical replay, and prints a checker command for the receipts it wrote.

What is not done

The checker ships inside the same installed artifact as the product, so it is not an independent external check. seal verify needs a network fetch on first use or a warm cache. There is no durable operator signing key. Seal checks authorization, not intent — if a person approves a harmful request, it runs — and even a signed receipt is tamper-evident, not tamper-proof. No one outside the project has run any of this yet.

Repositories

  • seal — the product a developer installs; the demo and CLI entry point.
  • seal-assurance-kit — the pinned runtime the product fetches by commit and hash; runs with Node alone.
  • seal-check — a browser checker for the family’s kernel receipts; a different program from the v1.1 receipt checker, which ships inside the product artifact.
  • mcp-seal-aria — the frozen source of the decision rule, archived at a fixed commit.
  • seal-host — the build and evidence host: the mediating process, signed releases, checksums, and provenance.

Other work

attention-lean

A Lean 4 / Mathlib formalisation of hard-attention expressivity over Boolean cubes. The main theorem shows that for every odd n ≥ 5, strict majority needs at least (n+3)/2 attention heads — one more than its certificate bound — and the five-bit case is exact: k(maj₅) = 4. Structural proofs are kernel-checked with no sorry and no native_decide; enumerated cases are isolated and pinned separately.

SafeMesh

An embeddable library for state that must converge after network partitions. The verified claim is narrow and stated in-repo: five CRDTs (G-Set, G-Counter, PN-Counter, OR-Set, RGA/Text) carry Lean convergence proofs, tied to the Rust implementation by differential tests against a Lean-generated oracle. The event log, wire encoding, and language bindings are tested engineering, not proofs.

Technical note

For the reader who wants the proof story behind Seal: the decision rule is a Lean 4 development, and the theorems cover the mediation kernel — non-bypass and a verifiable record — not the whole deployed system. The family’s Rust and wasm artifacts (seal-host and the assurance kit) are connected to the proofs by byte-exact conformance tests over a corpus, not by a theorem about every compiled instruction; the v1.1 Node artifact described above is not covered by that corpus, and its guarantees are the tests in its own repository. What is proven, tested, assumed, and not claimed is kept in one table: the claims matrix.
